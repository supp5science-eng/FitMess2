## Decisions made
- Used OFF's "search-a-licious" search API (`https://search.openfoodfacts.org/search`) instead of the documented `https://world.openfoodfacts.org/api/v2/search` endpoint named in tech-decisions.md/mcp-registry.md: the v2 `/search` endpoint returned HTTP 503 ("Page temporarily unavailable") for every query tried live during implementation (confirmed via direct `curl`), while search-a-licious (the backend OFF's own website search now uses, confirmed reachable and correctly returning Serbian-tagged results with a live `curl` test) answered reliably. Both are OFF's own public, keyless APIs — this is a same-provider endpoint swap to route around a live-service outage, not a scope change. Query: `countries_tags:"en:serbia"`, matching the `countries_tags` field the classic API also exposes.
- No `product_name_sr` (Serbian-localized name) values were observed in any live OFF results for Serbian-market products sampled during implementation — OFF simply doesn't have that field populated for this market yet. The mapping code still prefers it when present (per the clarified field-mapping answer "product_name -> name_sr (or the Serbian/Latin name if available)"), falling back to the generic `product_name` (already Latin-script for virtually all OFF entries) when absent, which is what actually happened for all 1328 imported rows.
- `common_units` is always `[]` for OFF-imported rows — OFF has no reliable structured "common portion" data comparable to the curated seed dataset's hand-authored `{label, grams}` units; leaving it empty rather than guessing avoids inventing false portion data. F024 (search) and later food-detail UI must handle an empty `common_units` array gracefully regardless of source (already true of the schema — the column defaults to `'[]'::jsonb`).
- **Pagination bug found and fixed live in this session**: the initial "load existing barcodes" query used `.select("barcode").not("barcode","is",null)` with no `.range()`, which silently truncates at PostgREST/Supabase's default 1000-row response cap once `public.foods` passes 1000 barcoded rows (it now has 1328+350=1678 total, ~1670 with barcodes). This was caught by actually re-running the script live and observing the in-memory dedup count (1000) not matching the true DB count (1328) — the DB-level `upsert(..., ignoreDuplicates: true)` safety layer prevented any actual duplicate rows from being written, but the run's reported "skipped-duplicate" number was wrong before the fix. Fixed by paging the existing-barcode fetch in 1000-row chunks via `.range()`. Re-verified live after the fix: a third run correctly reported all 1328 as duplicates with 0 new writes. This two-layer idempotency design (in-memory pre-filter + DB-enforced upsert) is what let the bug surface as a reporting-only issue rather than a data-correctness issue, and it's why the DoD's "re-run does not duplicate rows" claim is trustworthy even before the fix — but the fix makes the summary counts accurate too, which the DoD's "evidence artifact" (script log) also requires.
- Capped the import at `IMPORT_CAP = 2000` submitted rows (clarified Round-B decision #13) and `MAX_PAGES = 40` (safety ceiling independent of OFF's reported count) — in practice OFF only has 2994 Serbia-tagged products total, of which 1328 (~44%) pass the AS-035 quality filter, so neither cap was actually the limiting factor this run; the whole run (30 pages + upserts) completed in well under 2 minutes.
- Retry/backoff: each OFF page fetch retries up to 5 times with exponential backoff (800ms base, doubling) on non-2xx or network failure; if all retries are exhausted the script stops paginating but still writes whatever was already collected (partial-progress-safe), per the spec's resilience requirement. Not exercised live this session (OFF/search-a-licious was reliably reachable throughout), but is unit-independent of the DB-write path and was code-reviewed against the same pattern used elsewhere.
- Reused the exact `loadDotEnvIfPresent()` / admin-client-construction pattern from `scripts/seed-foods.ts` (F021) for consistency and because it's already proven correct in this repo (never overwrites `process.env`, never logs a credential value).
