## Decisions made
- **Retry ONLY on rate-limit-shaped errors, never on any other error.** `isAuthRateLimitError` checks `status === 429`, `code === "over_request_rate_limit"`, or a case-insensitive "rate limit"/"too many requests" substring in the message. A wrong password, an unconfirmed-email rejection, an RLS denial, etc. all return immediately on the first attempt, exactly as before this change — this was essential to keep every existing negative-path assertion (e.g. F013's `email_not_confirmed` test, F019's own "wrong confirmation phrase" and "already deleted" tests) proving the SAME thing it proved before, with zero risk of a genuine failure being silently retried into eventually looking like a pass.
- **Hard-capped, non-infinite retry.** `maxAttempts` defaults to 5 (a small, bounded number) and every computed delay is capped at `maxDelayMs` (default 4000ms) regardless of how large the exponential term grows — verified by a dedicated unit test (`test_AS_004_respects_maxDelayMs_as_a_hard_cap...`) that spies on `setTimeout` and asserts every observed delay stays under the cap even with an artificially large `baseDelayMs`. A persistent, non-transient outage still fails clearly (the last attempt's real error is returned) rather than hanging — matches the mission's explicit "NO infinite sleep loop" instruction.
- **Generic and Database-type-agnostic.** `SupabaseClient<Db = unknown>` rather than importing this project's own `Database` type into the helper — keeps `src/lib/test-utils/auth-retry.ts` reusable verbatim by any future M3+ integration test file with a different or no `Database` generic, per the spec's "reusable by future integration tests" requirement.
- **Did NOT restructure `src/app/(app)/profil/pravila/__tests__/actions.integration.test.ts` (F017/AS-029)'s 5-user test layout** (toggle, edit, cross-user x2, regenerate), even though it's this suite's single biggest per-file auth-call count. Evaluated merging the toggle/edit scenarios into one test to save 1 user, but rejected it: (a) the actual total call volume across the WHOLE suite is small (rough count: ~28 `admin.createUser` calls + ~34 `signInWithPassword` calls project-wide, comfortably inside the now-2000/5min raised limit — see Notes below), so this file alone was never going to be the deciding factor in whether the suite passes; (b) merging two independently-named `it` blocks (each already named after its own scenario, matching this repo's "test name references assertion ID" convention) to save one `admin.createUser` call is not "cheap" in the sense the spec meant — it would reduce test-failure localization (a future regression in "toggle" vs "edit" would no longer fail independently) for a marginal, unnecessary call-count reduction. The spec's "where cheap" qualifier is exactly the signal to skip this restructuring. The retry helper (applied to every call site in this file) is the actual durable fix; the call-count reduction was explicitly secondary ("Where cheap... reduce").
- **Left F013's one intentionally-failing `signInWithPassword` call (the unconfirmed-user negative control) as the raw, unwrapped client call**, with an inline comment explaining why: `signInWithPasswordRetry` would have passed it through unretried anyway (an `email_not_confirmed` error is not rate-limit-shaped), so wrapping it would have been functionally identical but would have obscured, at a glance, that this specific call is SUPPOSED to fail. Every other call site in every file was wrapped for consistency and defense-in-depth.
- **Did not touch `src/lib/auth/core.ts`'s `signInEmailPassword`/`signUpEmailPassword`** (called indirectly by `auth-flow.integration.test.ts`) — these are product code, not test infrastructure, and out of this feature's "Touches" scope (a test-infra hardening feature, not a product-code change). The direct `admin.auth.admin.createUser`/`deleteUser` calls in that same file, which ARE raw test-only Supabase Auth calls, were wrapped.

## Autonomous decisions
AUTONOMOUS_DECISION: Chose `maxAttempts: 5` / `baseDelayMs: 300ms` / `maxDelayMs: 4000ms` as the retry helper's defaults. The spec asked for "a few retries, jittered, capped" without exact numbers; these give a worst-case added latency per call of roughly 300+600+1200+2400 ≈ 4.5s of backoff (before the 5th and final attempt) which is small relative to this suite's ~135s total runtime, while still giving a genuinely transient rate-limit spike several real chances to clear before failing. Exposed as overridable `AuthRetryOptions` per-call so a future test can tighten or loosen this if needed.
AUTONOMOUS_DECISION: Did not reduce the total number of test users created in any file beyond what already existed (i.e., did not restructure any file's test layout to merge independent `it` blocks) — justified in "Decisions made" above. The retry wrapper (applied everywhere) is the actual durable fix requested; call-count reduction was explicitly framed as "where cheap" in the spec, and the one file where it might have mattered (F017/AS-029) wasn't worth the test-isolation tradeoff given the now-generous 2000/5min limit.
