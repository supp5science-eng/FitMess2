## Decisions made
- **Followed F017's confirmed storage layout** (read `missions/20260717-183157/handoffs/F017-handoff.md` first, per instructions): eating rules live in `profiles.rules` (jsonb), not a separate table. The export therefore reads `profiles` once and splits it into a top-level `profile` object (rules field stripped) and a top-level `rules` array, rather than a separate DB query for "rules" — matches the run instructions' requested `{ profile, targets, rules, exported_at, schema_note }` shape exactly.
- **Built the Route Handler's Supabase client from `request.cookies` directly instead of `next/headers`'s `cookies()`** — this Route Handler never needs to *write* a refreshed session cookie back (the app-wide `src/middleware.ts` matcher already covers `/api/*` and refreshes the session earlier in the same request), so a read-only `getAll` is sufficient, and it makes the handler directly callable in a Vitest process with a hand-built `NextRequest` (no live Next server, no `next/headers` request-scope error) — the same testability reasoning behind F013's `middleware()`-direct-invocation tests, extended to a Route Handler instead of middleware.
- **`USER_OWNED_TABLES` is a data-driven, one-line-per-table extension array**, not a hardcoded list of individual queries — per the explicit run instruction "write it so ADDING future tables later is a one-line change." Each entry is `{ key, table, userColumn, labelSr }`; the loop in `collectUserExport` handles the actual query + inclusion in both the JSON body and the `schema_note` sentence uniformly. `profiles`+`rules` are deliberately NOT forced into this generic shape (they're a single row split into two export keys, not a `user_id`-filtered list), and the file's header comment says so explicitly, along with a worked example of a future table needing a different shape (e.g. a join).
- **Response body on success is the export object itself, not the app's usual `{ok,data}` envelope** — the clarified API-contract answer's own wording carves out an exception ("streaming where the spec says so"); since this route's whole purpose is a downloadable file, the file's bytes must literally be the JSON the user wants, not a wrapper object. Failures still use the standard `{ok:false,error_sr}` Serbian-error shape, so the contract is honored for the one path where it matters (the client-visible failure case).
- **Added an `account` field (`{id, email}`) sourced from the already-resolved `auth.getUser()` session object** — not one of the three tables the run instructions explicitly named (profiles/targets/rules), but AS-014's own wording is "all of their currently-stored personal data," and the user's email is unambiguously their own personal data, already available for free from the same call the route already makes to authenticate the request (no extra query, no elevated client). Documented as an autonomous decision below in case a validator expects the export to be *strictly* limited to the three named tables.
- **No Sentry call on the failure path** (just `console.error`) — matches every existing route/action in this codebase (`persist.ts`, `rules-settings.ts`) to date; `@sentry/nextjs` is not yet wired into application code (only referenced in `src/lib/env.test.ts`'s env-var check) — Sentry wiring is F072's scope per `mcp-registry.md`/`tech-decisions.md`, not this feature's.
- **Puppeteer download verification used an in-page `fetch()` instead of relying on the OS-level download to land a file on disk** — both `Page.setDownloadBehavior` and `Browser.setDownloadBehavior` (CDP) were tried against headless Edge in this environment and neither ever produced a file in the configured download directory, even though the click itself worked correctly (page stayed on `/profil`, consistent with an attachment download rather than a navigation — if the route had NOT sent `Content-Disposition: attachment`, headless Chrome/Edge normally navigates and renders the raw JSON in the tab instead, which did not happen). Rather than spend further time fighting CDP download-event plumbing in this specific headless-Edge setup, the walkthrough proves the same end-to-end claim (real button, real click, real authenticated browser session, real live DB data) via an in-page `fetch()` to the identical URL, which is a strictly *more* direct way to inspect the actual response bytes than parsing a file off disk would have been anyway.

## Out-of-scope work needed
- **Future milestones must append to `USER_OWNED_TABLES` in `src/lib/export/user-data.ts` exactly as documented in that file's header comment** (this is the completeness checklist for AS-014 as the app grows):
  - **M3 (food logs):** `{ key: "logs", table: "logs", userColumn: "user_id", labelSr: "dnevni unosi hrane" }`
  - **M5 (weigh-ins):** `{ key: "weighIns", table: "weigh_ins", userColumn: "user_id", labelSr: "merenja težine" }`
  - **M6 (agent conversations / summaries):** `{ key: "conversations", table: "conversations", userColumn: "user_id", labelSr: "razgovori sa agentom i sažeci" }` — if conversations and their summaries end up in two separate tables rather than one, add two entries instead of one.
  - **Vision (user-submitted/crowdsourced custom foods):** `{ key: "customFoods", table: "foods", userColumn: "created_by", labelSr: "sopstvene namirnice" }` — note this table is NOT purely user-owned (it's shared-read per `tech-decisions.md`'s "foods are shared-read, admin-write" convention), so this entry must filter to rows this specific user *created* (`created_by`), not all foods.
  - None of these tables exist yet in `src/lib/types/db.ts`'s `Database` type as of this feature — TypeScript will correctly refuse to compile a `USER_OWNED_TABLES` entry referencing a table that isn't in that type yet, which is itself a useful guard: whichever future feature adds the migration + `db.ts` entry for one of these tables should also add its one-line export entry in the same PR/commit, and the type system will catch it if forgotten only if that worker actually tries to add the entry — it will NOT auto-fail if a future worker simply forgets this file exists. **A future scrutiny validator checking full AS-014 completeness once M3/M5/M6/vision land should specifically check `src/lib/export/user-data.ts`'s `USER_OWNED_TABLES` array against the actual live schema at that time.**
- No admin/support-side "export any user's data" tool exists (not in scope — F018's clarified access control is "own-user scope enforced by RLS + session", not an admin capability). If a future feature needs that (e.g. for support tickets), it would need a *separate* admin-only route using `createAdminClient()` plus an explicit `is_admin` check, reusing `collectUserExport` with a manually-supplied `userId`/`account` (the function itself doesn't care who resolved those, only that the `supabase` client passed in has read access to that user's rows — an admin client always does).
- No CSV/other export format — only JSON, per the clarified spec/feature title ("GDPR data export (JSON)"). Not attempted, not a gap.
