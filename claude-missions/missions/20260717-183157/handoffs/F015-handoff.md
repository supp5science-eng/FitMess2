## Decisions made
- **Collects `ageYears`, not `birthYear`, even though `profiles.birth_year` is the persisted column.** AS-019's own text says the wizard collects "age", and `src/lib/budget/engine.ts`'s `bmr()` (F014) takes `ageYears` directly — carrying age (not a derived birth year) to F016 is exactly what the very next consumer needs. F016 is responsible for converting `ageYears` -> `birth_year` at persist time; this feature never touches the database at all (see the clarified spec's "do not implement the final save here").
- **All wizard state lives in React `useState` inside `OnboardingWizard`, not a URL step param.** The clarified spec offered either option ("URL step param or client state"). Since the wizard container never unmounts between steps — only which step's JSX renders changes — client state alone already satisfies "nothing is lost moving Back/Dalje" (proven by `test_AS_019_going_back_and_forward_keeps_the_previously_selected_sex`), with no extra routing/query-parsing code needed for the 6 in-wizard steps themselves.
- **The final hand-off to F016 goes through a query string on `/onboarding/pregled`** (`buildOnboardingSummaryUrl` in `src/lib/onboarding/types.ts`), not a draft DB row. This was the lower-risk option within this feature's scope: no new migration/table, no risk of accidentally setting `onboarded_at` early, and F016's own clarified spec ("Server-fetched props") fits a server component reading `searchParams` naturally. `/onboarding/pregled` does not exist yet (F016's job) — clicking "Završi" during the live walkthrough genuinely navigates the browser there with all 7 values correctly encoded (captured in `evidence/F015/puppeteer-walkthrough.log`), then 404s, exactly mirroring the precedent the F013 handoff set for `/onboarding` itself before this feature existed.
- **"Cilj" (step 6) validates target weight against current weight collected in step 4** (`validateGoal(targetWeightKg, timeframeWeeks, currentWeightKg)`), rejecting a target that is not strictly below the current weight ("Ciljna težina treba da bude manja od trenutne.") — this is the "target weight sane vs current" rule from the clarified spec, and matches the product's fat-loss framing (the spec's own example is "-6 kg za 12 nedelja", a loss goal). `src/lib/budget/engine.ts`'s `planGoalAdjustment` already handles a `weightDelta <= 0` maintenance/gain case gracefully if a later feature ever wants to relax this at the wizard level — this feature's own validation is intentionally the stricter, product-appropriate front door.
- **Validation ranges (age 14-100, height 120-230cm, weight 35-300kg, timeframe 1-104 weeks) are the front-door rules a real user's typed input hits first**, intentionally a bit tighter than `src/lib/budget/engine.ts`'s own defensive clamp bounds (13-100 / 100-250 / 30-300, which exist as a last-resort safety net for data that already slipped past this validation). Exact numbers per the clarified spec's stated ranges.
- **Interpreted the generic "ui" clarified answers (loading skeleton / empty state / server-fetched props) in light of this specific feature's actual shape**, since F015 has no server data to fetch and nothing to persist (a pure client-side data-collection form, unlike F016's later summary screen which does fetch/persist): "empty state" = the wizard's very first render (step 1, pol) already IS the friendly Serbian prompt with a clear next action (the Dalje button); "failure handling" = the inline Serbian validation error + retry affordance, since there is no server call in this feature's scope that could fail. Documented explicitly as an autonomous decision below, since these generic clarified answers were written before knowing this feature's exact shape.
- **`OptionGroup` (pol, aktivnost) is a plain `role="radiogroup"`/`role="radio"` built from real `<button>` elements**, not a shadcn Radio primitive (none exists in this repo's `components/ui/` yet) — keeps every option keyboard-reachable (Tab/Enter) with zero extra key-handling code, per the accessibility clarified answer (AS-128).
- **Discovered and documented (did not fix) a pre-existing client-router URL/pathname mismatch** immediately after sign-in: `signInAction`'s `redirect("/danas")` (F011) plus the F013 middleware's server-side 307 to `/onboarding` means the browser's address bar and `usePathname()`-derived state briefly show `/danas` while the actually-rendered content is the onboarding wizard (confirmed live: `window.location.pathname` reads `/danas`, but a `page.reload()` at that exact moment correctly lands on `/onboarding`). This does not affect AS-018 (the user is never shown `/danas`'s real content, only the onboarding wizard) or any assigned assertion, and the root cause lives entirely in F011's `signInAction` redirect target / Next.js 16.2's server-action-redirect-plus-middleware interaction, neither of which is in this feature's "Touches" list — flagged below rather than silently patched.
