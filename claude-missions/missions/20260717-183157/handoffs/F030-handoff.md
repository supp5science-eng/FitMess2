## Decisions made
- **Self-hosted the ZXing WASM decoder binary (`public/wasm/zxing_reader.wasm`) instead of using the package's default jsDelivr CDN serving path.** `tech-decisions.md` says "zero API cost," and the clarified spec's verification note asks to prove "no network requests made during decode." The package's out-of-the-box behavior fetches the ~1MB `.wasm` file from a third-party CDN on first use — technically not a "per-scan" cost, but still an external dependency at runtime and a CSP/offline concern. Self-hosting via `prepareZXingModule`'s `locateFile` override (documented, first-class package feature, not a hack) makes the "100% client-side, same-origin" claim literally true end-to-end, not just "no cost after the first CDN round trip."
- **Generated the AS-052 test fixture with zxing-wasm's own writer rather than hand-crafting or downloading a barcode image.** This produces an authentic, checksum-valid EAN-13 PNG (verified by hand: 12-digit weighted sum 83, check digit `(10 - 83%10) % 10 = 7`, matching the fixture's value "5901234123457" — the canonical Wikipedia EAN-13 example) using the SAME underlying ZXing library the reader uses, so the reader test is proven against a real barcode image, not a synthetic/fake one. The fixture is a committed, deterministic binary (1.3KB), not generated at test time, so the suite has no dependency on `zxing-wasm`'s writer subpath at test-run time.
- **The AS-052 decode test runs under Vitest's `node` environment (`// @vitest-environment node`), not the project's default `jsdom`.** Investigated first: `barcode-detector`'s Blob-decode path branches on `globalThis.Image` being present. jsdom DOES define a stub `Image` whose `.decode()` cannot actually decode real image bytes (no real image codec in jsdom), so the ponyfill throws `"Failed to load or decode Blob."` under jsdom. Plain Node has no `Image`/`createImageBitmap` globals at all, so the ponyfill instead hands the raw PNG bytes straight to the ZXing WASM reader's own built-in image decoder — the exact same code path a real browser takes internally, just reached via a different internal branch. This is a TEST-ENVIRONMENT-ONLY concern; verified the real runtime code behaves identically in an actual browser via the headless-Edge screenshot evidence (`evidence/F030/01-scanner-viewfinder-375px.png` shows a real, successful `detect()` loop running with zero errors against a real camera stream in a real Chromium-based browser).
- **Restricted the `BarcodeDetector`'s `formats` option to `["ean_13", "ean_8"]`** rather than the package's default "detect everything." FitMess only ever needs product barcodes (everything in the `foods` table is EAN-13; EAN-8 covers short-format packaging) — narrowing formats is faster per frame and avoids false-positive detections of unrelated barcode types (QR codes, etc.) that might appear in a camera's field of view.
- **Found and fixed a real race-condition bug during manual verification, not just in code review:** the live scan loop's very first `decodeBarcode(video)` call can fire before the `<video>` element has decoded its first real frame, which the decoder reports as `InvalidStateError` ("Invalid element or state"). Originally this flipped the UI straight into the AS-058-adjacent "error" state on nearly every real scan session (caught this via the `01-scanner-viewfinder-375px.png` evidence screenshot showing the error screen instead of the live viewfinder). Fixed by treating `InvalidStateError` specifically as "no frame yet, try again next tick" (silently skip, keep scanning) rather than a genuine decode failure — any OTHER error still surfaces the real Serbian error state with retry. Added `test_scanner_treats_a_not_ready_video_frame_as_a_silent_retry_not_a_scary_error` to `barcode-scanner.test.tsx` to cover this specifically, and re-captured the screenshot evidence after the fix to confirm the real live scanner UI now renders correctly.
- **`BarcodeScanner` only emits the decoded GTIN via an `onDetected(code: string)` callback prop — it never navigates, looks anything up, or logs anything itself.** This matches the clarified scope exactly ("scan->lookup->log is F031 next") and the DoD's side-effect verification requirement ("no unintended navigation or global state mutation"). `ScanScreen` (the actual `/dodaj/skener` composition) owns what happens after detection; see "Notes for the next worker" for exactly how F031 should extend this.
- **Chose a real, non-blank post-scan confirmation screen (showing the exact scanned GTIN) over silently doing nothing or auto-navigating anywhere**, since F031 (lookup + log) doesn't exist yet. This proves the scan genuinely worked (the whole point of this feature) without pretending a not-yet-built product-lookup flow exists.
- **Updated `AddSheet`'s `barkod` row and its test expectations** exactly as F028's own handoff instructed ("F030 ... should replace `AddSheet`'s `barkod` row's `href` ... and can leave everything else in `add-sheet.tsx` untouched") — this was pre-authorized cross-feature integration work, not scope creep.
