## Decisions made
- **`updateSession()`'s return type changed from `NextResponse` to `{ response, user, supabase }`.** The old shape only let a caller forward the refreshed-cookie response; F013 needs the resolved `user` (for `isEmailVerified`) and a cookie-bound client (for the `profiles.onboarded_at` read) from the *same* request without a second `createServerClient` call. This is the one non-additive change to existing code, and it was already flagged as needed in the file's own docstring (it literally said "the route-protection feature... should add a root `src/middleware.ts` that calls this"). No other caller of `updateSession` existed yet (confirmed via search — F011/F012 never wired a root middleware).
- **`decideRouteAccess` is a pure, framework-free function** (`src/lib/auth/route-protection.ts`) taking `{pathname, isAuthenticated, isEmailVerified, isOnboarded}` and returning `{action: "allow"}` or `{action: "redirect", to}`. This is the "unit-test the redirect-decision function in isolation" path from the run instructions, and it's the single source of truth `src/middleware.ts` delegates to — no redirect logic is duplicated between the two files.
- **Default-deny path classification.** Only the marketing home (`/`), `/prijava`, `/registracija*`, and `/auth/*` (the callback) are ever public; every other pathname — including future `(app)` routes not yet built (`/nedelja`, `/agent`, `/dodaj/*`, etc.) and any future API routes — is protected by default. This matches the clarified spec's "and future (app) routes" language and the codebase's existing fail-closed convention (e.g. `mapAuthErrorToSerbian`'s default case, RLS's own-row-only policies). A future worker adding a new page under `(app)` gets route protection for free with no middleware change needed.
- **`/auth/*` (the callback) is public but never "bounced away from"** even for a fully set-up user, unlike `/prijava`/`/registracija`. Reasoning: at the moment middleware runs for `/auth/callback`, the code hasn't been exchanged yet, so `user` is typically still null (falls into the public-path allow branch regardless); and forcing a hard redirect away from the callback for an edge case (e.g. an email-change confirmation link clicked while already signed in on another tab) would break that flow's code-exchange step entirely. Covered by `test_fully_set_up_user_hitting_the_auth_callback_route_is_not_bounced_away`.
- **The onboarding-status DB read only runs when the user is authenticated AND verified.** An anonymous or unverified request never touches the `profiles` table — it's redirected before that branch is reached, keeping the common (signed-out) case to exactly one Supabase Auth call (`getUser()`, already required for session refresh) with no extra round trip.
- **The unverified-branch live proof stops at "GoTrue never issues a session for an unconfirmed email/password account" (`error.code === "email_not_confirmed"`)** rather than trying to fabricate a live "authenticated-but-unverified" cookie. This is not a shortcut: GoTrue is designed so that state is unreachable through any real sign-in flow (proven live in the test), which means the middleware's `!verified` branch is genuine defense-in-depth for a session shape that cannot normally occur — its correctness is instead proven by the 10 pure unit-test branches in `route-protection.test.ts` (`isAuthenticated: true, isEmailVerified: false`), which exercise the exact same `decideRouteAccess` function `middleware.ts` calls.
- **Verified live sessions for the integration tests were built via `@supabase/ssr`'s own `createServerClient` + an in-memory `Map` cookie jar**, not hand-rolled cookie strings. `createServerClient`'s internal `onAuthStateChange` listener calls the provided `setAll` on `SIGNED_IN`/`SIGNED_OUT` (confirmed by reading `node_modules/@supabase/ssr/dist/main/createServerClient.js`), so the cookie names, values, and `base64url` encoding captured are byte-for-byte what a real browser session would carry — a faithful integration test without booting an actual HTTP server.
- **`ProfilPage` is a plain (non-`"use client"`) Server Component** with `<form action={signOutAction}>` — React 19's built-in server-action form handling needs no client JS for this, matching the "Redirects for page flows" API contract from the clarified spec (no JSON round trip needed for a page-level action).
- **Matcher excludes `_next/static`, `_next/image`, `favicon.ico`, `manifest.json`, and common static-asset extensions** (svg/png/jpg/jpeg/gif/webp/ico), following the pattern Supabase's own Next.js SSR guide uses, per the clarified spec's "keep the middleware matcher efficient" instruction.

## Autonomous decisions
AUTONOMOUS_DECISION: Chose default-deny (protect everything except an explicit public allowlist of `/`, `/prijava*`, `/registracija*`, `/auth*`) rather than an explicit protected-allowlist of just `/danas`, `/nedelja`, `/agent`, `/profil`, `/onboarding`. The clarified spec's "and future (app) routes" phrase implies new `(app)` pages should be protected automatically without a middleware change; default-deny also matches this codebase's established fail-closed conventions elsewhere (RLS own-row policies, `mapAuthErrorToSerbian`'s generic-fallback default case).
AUTONOMOUS_DECISION: Added the "bounce fully-set-up users away from `/prijava`/`/registracija` to `/danas`" behavior. The clarified spec's scope note says this "may" happen ("an already-authenticated user hitting /prijava may be redirected to /danas") — implemented it as a firm rule since it's better UX (no reason to show a login form to someone already logged in) and is the natural mirror image of AS-012's "afterwards protected pages redirect to login" (before sign-out, auth pages redirect to the app; after sign-out, protected pages redirect to auth pages).
AUTONOMOUS_DECISION: Did not act on the Next.js 16.2 "middleware -> proxy" deprecation warning surfaced during `npm run build` (see Out-of-scope work needed) — the clarified spec explicitly names `src/middleware.ts`, and unilaterally renaming the convention based on a single build warning (without deeper research into the new API's semantics) risked deviating from the clarified spec's explicit instruction. Documented for the orchestrator instead of overriding.
