## Decisions made
- **The DB-decision core (`resolveAdminSessionForClient`) is client-injectable**, exactly mirroring `src/lib/auth/core.ts`'s (F011) established pattern: it takes an already-constructed `SupabaseClient` rather than building one via `@/lib/supabase/server`'s `createClient()` (which needs a live Next.js request context via `next/headers`, unavailable in Vitest). This is what makes AS-059/AS-067 testable against the real live project from Vitest without mocking `next/headers`, and is also what a future admin Route Handler would reuse if it ever needed the raw decision without the `requireAdmin()`/`requireAdminApi()` wrappers.
- **Two separate guard shapes, one shared core** — `requireAdmin()` (redirects, never returns, for Server Components/layouts) and `requireAdminApi()`/`toAdminApiResult()` (never redirects, returns `{ok,status,error_sr}`, for Route Handlers/Server Actions) — matching this feature's inherited API contract ("Redirects for page flows; JSON {ok,error_sr} for actions"). `toAdminApiResult()` is exported separately from `requireAdminApi()` specifically so it can be exercised directly against an already-live-resolved session in tests without needing a Next.js request context — this is how AS-067's live proof works.
- **`profiles.is_admin` is read via the caller's own-row RLS `select`, no admin-bypass client and no new RLS policy needed.** F010's migration already grants an authenticated user `select` on their own profile row (`profiles_select_own`), and `is_admin` is just a column on that row — checking "is THIS caller an admin" never needs to see any OTHER user's row, so `createAdminClient()` is never used inside the gate itself. This matches F010's own handoff note ("No admin-bypass RLS policy was added ... Admin tooling (F033 `is_admin` gate...) is specified to use `createAdminClient()`") — narrowed here to: the *gate itself* doesn't even need that; only F034/F035's actual cross-user *mutations* will.
- **The denial page (`/nemas-pristup`) is deliberately NOT nested under `/admin`.** If it were (e.g. `/admin/nemas-pristup`), `src/app/admin/layout.tsx`'s own `requireAdmin()` call would run for that route too and redirect a denied visitor back into itself — an infinite loop. Placed as a top-level route instead (Next.js route groups/segments don't need to mirror folder nesting for URL protection — `src/middleware.ts`'s default-deny already protects it like any other page regardless of where it lives in the file tree).
- **`requireAdmin()`'s anonymous branch (`/prijava`) reuses `SIGNED_OUT_REDIRECT_PATH` from F013's `route-protection.ts`** rather than a new constant, keeping a single source of truth for "where a signed-out visitor goes." In practice this branch is defense-in-depth — `/admin` is already covered by F013's default-deny middleware, so an anonymous request should never reach `requireAdmin()` at all — but it's implemented and tested the same way F013 treats its own defense-in-depth branches (e.g. the unverified-email check).
- **No placeholder pages for `/admin/hrana`, `/admin/korisnici`, `/admin/troskovi`.** The run instructions explicitly say "placeholders/links are fine now" and these three sub-areas are F034/F035, F036, and F075's own scope respectively — building even minimal pages for them here would be scope creep into features that haven't run yet. This mirrors F005's own precedent (`bottom-nav.tsx`'s own comment: "routes may 404 for now").
- **No `puppeteer-core` package is installed in this repo** (confirmed via `npm ls puppeteer-core` — empty), despite F011/F012's handoffs referencing "puppeteer-core (Edge)" screenshot capture. Rather than adding a new dependency for one evidence-capture script, used Node 24's built-in global `WebSocket` + `fetch` to drive real headless Edge (`C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe`, confirmed present) directly over the Chrome DevTools Protocol — no new `package.json` dependency, no network install needed. The script created a page TARGET via `PUT /json/new` (the browser-level `webSocketDebuggerUrl` from `/json/version` only supports `Target`/`Browser` domain commands, not `Page`/`Network`/`Emulation` — this needed one fix mid-session, documented above).
- **The screenshot script needed to mark both test users `onboarded_at` non-null**, not just `is_admin` for the admin one — a freshly admin-created user's profile starts with `onboarded_at` still null (F010), and F013's middleware redirects any verified-but-not-onboarded visitor to `/onboarding` before the request ever reaches `/admin`. Without this, both screenshots initially landed on `/onboarding` instead of the intended pages — fixed and re-verified (see the two settled-pathname log lines in the terminal output during this session).
