## Decisions made
- **A single atomic `admin.auth.admin.deleteUser` call is the actual mechanism for "no partial writes,"** not a hand-rolled multi-step transaction. Since every personal-data table so far (`profiles`, `targets`) already has `references auth.users (id) on delete cascade` (confirmed by reading `supabase/migrations/0001_profiles.sql` directly, not assumed), deleting the `auth.users` row is a single Postgres statement whose cascade to child tables happens in the SAME transaction GoTrue's delete runs. This means if the call fails, literally nothing was touched — a stronger and simpler guarantee than attempting explicit row-by-row deletes first (which, if the deletion of the auth user then failed for any reason, would leave a genuinely bad partial state: personal data wiped but the account still able to log in). The clarified spec's "explicit/defensive" wording is honored by `cleanupResidualRows`, which runs AFTER a successful `deleteUser` as a read-then-delete safety net, never before — so it can never itself introduce the partial-state risk it's meant to guard against.
- **Server-side re-validation of the type-to-confirm phrase**, not just a client-side gate — the route rejects a mismatched `confirm` field with 400 before calling `createAdminClient()`/`deleteAccount` at all, so a request that skips the UI (e.g. a raw `fetch` from devtools) still can't delete an account without literally sending the correct Serbian confirmation string. Matches the clarified "zod-validated inputs; reject malformed with 400 + Serbian message" convention.
- **`DELETE_CONFIRMATION_PHRASE` lives in its own tiny `src/lib/account/constants.ts` module**, not exported from `route.ts` — `route.ts` imports server-only modules (`next/server`, `createAdminClient`, `deleteAccount`); importing anything from it into the `"use client"` dialog component would have pulled that whole server-only graph into the client bundle, violating `tech-decisions.md`'s "Secrets server-only; never in client bundle" rule even though the constant itself is not a secret. Caught this before it became a build error by tracing the import graph rather than just trying it and seeing what broke.
- **No new UI-library dependency for the dialog.** This codebase has no shadcn `Dialog`/Radix/base-ui dialog primitive installed yet (`src/components/ui/` only has `button`/`input`/`label`). Rather than adding one for a single feature, the dialog is a small hand-built `fixed inset-0` overlay + `role="alertdialog"` panel using local `useState`, matching this codebase's existing practice of small hand-built interactive pieces (e.g. `RulesScreen`'s inline edit rows) over adding new UI-library surface area for one use.
- **The route builds its Supabase client directly from `request.cookies`** (like F018's export route) rather than `next/headers`'s `cookies()` — same reasoning: this handler needs to be directly callable in a Vitest process with a hand-built `NextRequest`, no running Next server, no next/headers "outside request scope" error. Unlike F018's GET (read-only), this route ALSO needs to WRITE a cleared session cookie on success, so it captures `setAll`'s calls into an array and re-applies them onto the `NextResponse` it builds itself — the same two-phase read/write pattern `src/lib/supabase/middleware.ts`'s `updateSession` uses.
- **`signOut()`'s own error (if any) is swallowed, not surfaced.** By the time it's called, the auth user is already deleted — there may be nothing left for GoTrue to revoke server-side, but the goal at that point is just clearing the browser's now-stale cookie, and the deletion itself already succeeded; a `signOut()` hiccup should never turn a successful account deletion into a client-visible error.
- **Fixed a real regression this feature caused in a pre-existing test** (`src/app/(app)/__tests__/profil.test.tsx`): that F013 test renders `ProfilPage` directly via `@testing-library/react` with no real Next App Router context mounted, and `DeleteAccountDialog`'s `useRouter()` call threw `"invariant expected app router to be mounted"` once wired into the page. Added the same `next/navigation` mock `delete-account-dialog.test.tsx` uses. Caught by running the full suite before commit, per this repo's standing rule.

## Out-of-scope work needed
- **`USER_OWNED_TABLES`-style future tables must also get `on delete cascade` FKs to `auth.users`** as they land (M3 `logs`, M5 `weigh_ins`, M6 `conversations`, vision `foods.created_by`) for `deleteAccount`'s single-atomic-delete guarantee to keep covering them automatically — this feature's `deleteAccount` does NOT need code changes for that (the cascade does the work), but a future scrutiny validator or worker adding one of those tables should confirm the FK includes `on delete cascade`, the same way F010's migration already does for `profiles`/`targets`. If a future table is NOT owned via a simple `user_id` FK (e.g. shared/crowdsourced content a user merely contributed to, like custom foods a user submitted but others may reference), it should NOT cascade-delete on account removal — per this feature's own clarified spec ("Shared/crowdsourced data the user contributed ... should NOT be deleted later"), such a table should instead null out or anonymize the `submitted_by`/`created_by` reference (an `on delete set null` FK, not cascade) rather than delete the shared row. No such table exists yet as of this feature (custom foods land in M3/M5 per the clarified spec), so no anonymization hook was added here — flagging this explicitly so whichever future feature adds that table gets the FK direction right the first time instead of accidentally cascading and destroying data other users still reference.
- **No "delete my account" entry point exists anywhere except `/profil`** (no email confirmation step, no cooling-off period, no re-authentication/password re-entry prompt) — the clarified spec's failure-handling/access-control answers didn't ask for either of those, and AS-015/AS-016's wording doesn't require them; noting it in case a future privacy/security review wants a stronger confirmation ritual (e.g. re-enter password) for such a destructive action.
- **Admin-side "delete any user's account" tooling** (e.g. for support/abuse handling) does not exist — out of this feature's scope (clarified access control is "own-user scope," not an admin capability). If needed later, it would be a separate admin-only route using `createAdminClient()` plus an explicit `is_admin` check, reusing `deleteAccount` with an admin-supplied `userId` instead of a session-resolved one (the function itself doesn't care who resolved the id, same reasoning F018's handoff documented for `collectUserExport`).

## Autonomous decisions
AUTONOMOUS_DECISION: Chose a single atomic `admin.auth.admin.deleteUser` call (relying on the already-verified `on delete cascade` FKs) as the actual "no partial writes" mechanism, with defensive residual-row cleanup running only AFTER a successful delete — rather than the more literal reading of the clarified spec's ordering ("deletes their personal-data rows ... deletes the auth user itself") as "delete profiles/targets rows first, then delete the auth user." Deleting the rows first and the auth user second would create a real partial-state risk if the second step failed (data gone, account still able to log in) — the chosen order avoids that risk entirely while still satisfying the "explicit/defensive" instruction via the post-delete verification/cleanup step. Justified in "Decisions made" above; easy to reverse if a future validator specifically wants row-deletion-before-user-deletion ordering, though doing so would reintroduce the partial-state risk this ordering was chosen to avoid.
AUTONOMOUS_DECISION: The dialog's Serbian confirmation phrase is "OBRIŠI" (imperative "delete" in ti-form spirit), matching the clarified spec's own example verbatim ("type 'OBRIŠI' or their email") — chose the fixed phrase over "type your email" since a fixed short phrase is less error-prone to type correctly on a 375px mobile keyboard than an email address, while still being unambiguous and hard to type by accident.
AUTONOMOUS_DECISION: No shadcn/Radix dialog primitive was added; the confirmation dialog is a small hand-built component. If a future feature needs a second real modal dialog elsewhere in the app, it may be worth introducing a shared `Dialog` primitive at that point rather than each feature hand-rolling its own — flagging so a future worker doesn't feel obligated to match this hand-built shape if a proper primitive becomes available.
