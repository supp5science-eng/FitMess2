## Decisions made
- **`signInWithOAuth` is called from a client component (`"use client"`), not a Server Action.** Unlike F011's email/password flow, the point of this call is that the *browser itself* navigates away to Google's consent screen — `@supabase/ssr`'s browser client does that internally (default `skipBrowserRedirect: false`) once it gets a `url` back. That only makes sense triggered from client-side JS, so `google-sign-in-button.tsx` builds the browser client via `@/lib/supabase/client`'s `createClient()`, not the cookie-bound server client.
- **Reused the existing `/auth/callback` route handler unchanged.** It already calls `exchangeCodeForSession(code)` unconditionally for any `code` param, with no provider-specific logic — this is the standard `@supabase/ssr` PKCE pattern and works identically whether the code came from an email-confirmation link (F011) or a Google OAuth redirect (this feature). No new route or route change was needed, satisfying the run instructions' "reuse the existing callback route" directive directly.
- **Added `isEmailVerified(user)` in `src/lib/auth/core.ts` as the shared, provider-agnostic confirmation gate**, and wired it into `signInEmailPassword`'s existing defensive check (previously an inlined `!data.user.email_confirmed_at`, now `!isEmailVerified(data.user)` — same behavior, now provably shared code). This directly answers the run instructions' "confirm the gate keys on that [`email_confirmed_at`], not on the email provider" — there is currently no other gate in the codebase (F013's route-protection middleware doesn't exist yet, confirmed by re-reading `src/lib/supabase/middleware.ts` and the F011 handoff's own "Out-of-scope work needed" note), so this is the one existing gate to make provider-agnostic, plus a reusable seam for F013 to call the same function later.
- **Simulated a Google-authenticated identity via `admin.auth.admin.createUser({ email_confirm: true, app_metadata: { provider: "google", providers: ["google"] } })`** rather than attempting any real OAuth flow, per the run instructions' explicit guidance that this is how to test what's testable — this is structurally what GoTrue produces for a real Google sign-in (email pre-verified, `app_metadata.provider` set to `"google"`), and proves the profiles trigger and the confirmation gate both work correctly for that shape without needing a real Google login.
- **Did not touch `supabase/migrations/0002_profiles_on_signup.sql` or the trigger it defines** — it is already provider-agnostic by construction (fires on any `auth.users` insert, regardless of how the row was created), confirmed by reading the migration's own header comment ("fires identically for email/password signUp, Google OAuth, and admin.createUser()") and now also proven by this feature's live test. No migration was needed for this feature.
- **Did not add a root `src/middleware.ts` or otherwise build route protection.** No protected app routes exist yet (per F011's handoff, `/danas` etc. still 404 — F013's scope), so there is currently nothing that could block a signed-in-but-technically-unconfirmed user from reaching app data; this feature's job was narrowly to make sure the one gate that *does* exist today doesn't discriminate against Google identities, which is now proven.
- **`redirectTo` is built from `window.location.origin`** (client-side), not a request header — mirrors `emailRedirectOrigin()`'s reasoning in `../actions.ts` but necessarily client-side since this call only ever runs in the browser. Works unchanged in dev (matches the live project's `uri_allow_list`, unaffected by this feature) and after the eventual Vercel deploy, with no new env var.
- **Kept the visual divider ("ili") + button inside `GoogleSignInButton` itself** rather than duplicating markup in both pages, so `/prijava` and `/registracija` stay in sync by construction; consistent Serbian "ti"-adjacent copy and the existing `outline` button variant / theme tokens from `src/components/ui/button.tsx` (F005 theme), no new UI primitive added.
- **Used `npx -p puppeteer-core node <script>` for screenshots (not added as a project dependency)**, matching F011's precedent of not committing a browser-automation dependency the app itself never needs at runtime.
