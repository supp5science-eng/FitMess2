## Decisions made
- **Chose a `rules` jsonb column on `profiles` over a separate `eating_rules` table**, per the clarified spec's stated preference. Rules are a small (3-5 element), user-owned, non-relational list with no need for independent RLS policies, foreign keys, or per-row history — they already travel with the rest of onboarding state on the same row, and are already covered by `profiles`' existing own-row RLS policies (`supabase/migrations/0001_profiles.sql`, AS-013) with zero new policy needed. Verified live (see Commands run) that the column exists exactly as `jsonb not null default '[]'::jsonb`.
- **Rule selection (`generateRules`) is a fixed catalog + eligibility predicates, not an LLM call or randomness** — matches tech-decisions.md's money-math-adjacent "AI calls are server-side only and never compute deterministic numbers" spirit extended to rule *selection*: the same profile always yields the same rules, is unit-testable against exact expected ids, and needs no Gemini API call/cost for what is fundamentally a rules-based recommendation. Algorithm: always start with 2 universal "anchor" rules (protein, povrće), add every catalog rule whose `eligible(profile)` predicate matches (activity level, deficit aggressiveness, macro-clamping, timeframe, weight-loss magnitude) up to the 5-rule cap, then pad with more universal rules if fewer than 3 total were selected — guarantees the AS-028 "3-5" bound for every possible profile, including ones that match zero conditional rules.
- **Rule generation is hooked directly into `persistOnboarding`** (`src/lib/onboarding/persist.ts`, an existing F016 file), not a separate "generate rules" step the user has to trigger. This was outside F017's generic clarified "Touches: New page/components + reads the relevant lib/API" answer (a UI-type-feature default written before this feature's exact shape was known), but the run-instructions explicitly said "Generate 3-5 rules for a user based on their profile **at onboarding completion** (AS-028) ... hook rule-generation into it if appropriate" and AS-028's own text ("onboarding completion yields 3-5 rules") requires the write to happen at that exact moment — there is no other point in the app where a user's full onboarding profile (sex/age/height/weight/activity/goal) first becomes available together. The change to `persist.ts` is a small, additive one (one new import, one computed value, one new field in the existing `profiles` update payload) — no existing behavior (AS-020/AS-031) was altered, confirmed by re-running F016's own `persist.test.ts`/`actions.integration.test.ts` unmodified and green.
- **Added a "Generiši pravila" / "Generiši ponovo" regenerate action** (`regenerateRules` in `src/lib/profil/rules-settings.ts`) beyond the minimum AS-029 scope. This exists for two concrete reasons, not scope creep for its own sake: (1) it **is** the clarified "Friendly Serbian empty state with a clear next action" requirement for a profile whose `rules` column is still the migration's `[]` default (any user who somehow reaches `/profil/pravila` without having gone through the post-F017 onboarding path); (2) it reuses the exact same F014-engine composition (`bmr` → `tdee` → `planGoalAdjustment` → `macroTargets`) `persistOnboarding` uses, so "regenerate" is provably not a different code path producing different results for the same underlying profile.
- **The optional day-structure guidance (`DayStructureGuidance`) is a fixed 25/35/10/dinner-remainder kcal split**, read-only, with no toggle or edit control and explicit "Ovo je samo orijentacija, ne obaveza" (this is only orientation, not an obligation) copy — directly matching the clarified spec's "keep it clearly optional, never an obligation." Deliberately visually distinct (dashed border, muted background) from the editable rules list above it so it doesn't read as another rule to toggle.
- **Toggling a rule persists immediately** (no separate "save" step for toggles), while **editing text requires an explicit "Sačuvaj"/"Otkaži" step** — a toggle is a single unambiguous binary action a user expects to take effect instantly (matches the settings-screen convention elsewhere in the app), while free-text editing needs a moment to actually type before committing, and an accidental keystroke-by-keystroke save would be both wasteful (a network call per character) and unpredictable (what does "save" mean mid-edit before the user is done). Both paths funnel through the same `persist()` helper and the same server action, so there is exactly one write path either way.
- **Optimistic local state with revert-on-failure** (clarified data-shape answer: "Server as source of truth; small client state (form/optimistic) only") — a toggle/edit updates the on-screen state immediately, then a `useTransition`-wrapped server-action call persists it; a failed save reverts the local array to its pre-change value and shows an inline Serbian error, so the UI is never left showing a state that silently failed to save.
