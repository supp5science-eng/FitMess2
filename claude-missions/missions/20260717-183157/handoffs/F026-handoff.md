## Decisions made
- **`PATCH /api/logs/[id]` re-fetches the referenced food's LIVE per-100g values server-side** (never trusts a client-submitted macro number, and never reuses the log row's own stale snapshot) — same "money-math rule" posture as F025's `POST /api/logs`. If `logs.food_id` is null (the referenced food was since deleted — a real, if rare, scenario since `foods.id ... on delete set null` on `logs.food_id`), the edit is rejected with a friendly Serbian 404 (`LOG_FOOD_UNAVAILABLE_ERROR_SR`) rather than silently reusing a stale number or crashing — this case isn't covered by a live integration test (would require deleting a food mid-test via the admin client, adding complexity for an edge case the clarified spec doesn't call out), but the code path exists and is documented here for a future worker who hits it.
- **Cross-user PATCH/DELETE both return 404, not 403** — RLS (`logs_update_own`/`logs_delete_own`) silently filters out rows that aren't the caller's own, so this route code cannot distinguish "this id doesn't exist" from "this id belongs to someone else" without a second, RLS-bypassing lookup it deliberately never makes (that would defeat the point of relying on RLS as the enforcement mechanism). 404 for both cases matches the existing `FOOD_NOT_FOUND_ERROR_SR` precedent from F025's `POST /api/logs` and never leaks whether a given id exists for another user. The verification section's "assert 403/denied" is satisfied by "denied" — the integration tests assert `expect([403, 404]).toContain(response.status)` and, more importantly, that the row is provably unchanged/still-present afterward.
- **`DELETE`'s own-row check uses `.delete().eq("id", id).select("id")`** rather than a plain `.delete()` — Postgrest's default response for a delete matching zero rows (nonexistent id, or an id RLS filtered out) is `{ error: null, data: null }`, NOT an error, so without selecting the affected row(s) back a cross-user delete attempt would silently "succeed" with zero effect instead of being reported as not-found/denied.
- **`findMatchingCommonUnit`** (new pure helper in `portions.ts`) lets the edit sheet pre-select "2 parčeta" instead of always falling back to a raw grams entry when re-opening an entry that was originally logged via a common unit — not explicitly required by AS-044's text, but directly serves the clarified spec's "pre-loaded with the existing entry's food + current grams/unit" instruction. Tries quantities in 0.5 steps (matching the picker's own quantity-input step) and returns the first unit (array order) that matches within a small floating-point epsilon.
- **Built `LogEditSheet`/`LogDeleteConfirm` as self-contained, dependency-free overlays** (own trigger button + open state, `role="dialog"`/`role="alertdialog"`), the exact same pattern F019's `DeleteAccountDialog` established — no shadcn Sheet/Dialog primitive exists in this codebase yet (`src/components/ui/` still only has button/input/label/badge/skeleton), and this keeps both components trivially droppable onto a meal card (`<LogEditSheet log={...} food={...} onSaved={...} />`) without F027 having to manage any open/close state itself.
- **No new database migration** — `supabase/migrations/0004_foods_logs.sql` (F020) already created `logs_update_own`/`logs_delete_own` own-row RLS policies; this feature is pure application code on top of an already-correct schema. Verified by reading the migration file directly (not via MCP — see Notes below) before writing any route code.
- **The delete confirm is a plain Yes/No dialog, not a type-to-confirm phrase** (unlike `DeleteAccountDialog`) — the clarified spec explicitly calls for "a small Serbian confirm," and deleting one log entry is much lower-stakes/more easily corrected (re-log the food) than deleting an entire account.
- **Reused a TEMPORARY, uncommitted demo page** (`src/app/(app)/dodaj/f026-demo/page.tsx`, created, screenshotted, then deleted within this same session) to produce the real-browser 375px evidence screenshots — `LogEditSheet`/`LogDeleteConfirm` have no dedicated route of their own (by design; F027 wires them onto its meal cards), so there was no existing page to navigate to for a real-browser screenshot. This keeps F026's actual shipped surface area exactly what the clarified spec scoped ("reusable edit/delete MECHANISM," no new screen) while still producing genuine full-stack evidence rather than a component-test snapshot.
