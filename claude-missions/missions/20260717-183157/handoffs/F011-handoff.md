## Decisions made
- **Core auth logic is client-injectable, not hardcoded to the cookie-bound server client.** `src/lib/auth/core.ts`'s `signUpEmailPassword`/`signInEmailPassword`/`resendConfirmationEmail` take a `SupabaseClient` parameter rather than constructing one via `@/lib/supabase/server`'s `createClient()` (which requires a live Next.js request context via `next/headers`). The `"use server"` actions in `src/app/(auth)/actions.ts` are thin wrappers that build the real cookie-bound client and delegate. This is what makes AS-008/AS-009/AS-017 testable against the live project from Vitest without mocking `next/headers` — mirrors the pattern F010 established (`profiles-rls.integration.test.ts` uses a plain `@supabase/supabase-js` client signed in for real).
- **Discovered empirically that Supabase's GoTrue backend already refuses to issue a session for an unconfirmed user** (`signInWithPassword` returns `error.code: 'email_not_confirmed'`, no session, no user — verified live, see evidence/F011/live-verification.log). This is the actual AS-009 enforcement mechanism for this feature (ahead of F013's full route-protection middleware): there is no session/cookie to intercept because Supabase never grants one. `signInEmailPassword` still has a defensive belt-and-suspenders check (`if (data.user && !data.user.email_confirmed_at) signOut()`) in case that behavior ever changes, but it is not what actually fires today.
- **Also discovered that wrong-password and unknown-email both already return the identical `invalid_credentials`/400 from Supabase itself** — verified live. `mapAuthErrorToSerbian` preserves this by branching only on `error.code`/`error.status`, never on `error.message` content, and fails closed (generic message) for any code it doesn't explicitly recognize.
- **Signup also treats an already-registered email as success** (same "check your email" response, same string), matching Supabase's own anti-enumeration signUp behavior (empty `identities` array / `user_already_exists` code, no new email sent) — this extends the clarified "never reveal whether an email exists" rule to signup, not just login, since AS-017's failure-handling answer was written at the feature level, not scoped only to the login form.
- **`uri_allow_list` on the live Supabase Auth config was empty and had to be updated** (PATCH via Management API) to `http://localhost:3000/**` so `emailRedirectTo`/`resend()` calls pointing at `/auth/callback` are actually accepted by Supabase, rather than silently failing at send time once real confirmation emails are used post-deploy-dev. `site_url` was already `http://localhost:3000` and was left unchanged (no production URL exists yet — see docs/deploy.md).
- **`emailRedirectOrigin()` reads the request's own `host`/`x-forwarded-host` headers (via `next/headers`) rather than a new env var.** Initially tried `NEXT_PUBLIC_SITE_URL`, but that failed `AS-003`'s "every env var referenced in source has a `.env.example` entry" test and would need to be kept in sync across dev/preview/prod manually. Deriving it from the request works correctly in dev today and will work unchanged after the eventual Vercel deploy, with zero new env var surface.
- **Preferred the trigger over an app-code insert for the profiles shell row**, per the clarified spec's explicit preference. `supabase/migrations/0002_profiles_on_signup.sql` adds a `SECURITY DEFINER` function + `AFTER INSERT ON auth.users` trigger (the standard, documented Supabase pattern for this), applied live via the Management API and behaviorally verified (admin-created user immediately has a matching `profiles` row, with no application code involved).
- **Fixed a regression in F010's `profiles-rls.integration.test.ts` caused directly by the new trigger**: that test's `beforeAll` used `admin.from("profiles").insert(...)` to seed user A's row, which now collides (`profiles_pkey` unique violation) with the row the trigger already auto-created the moment `admin.auth.admin.createUser()` ran. Changed that one call to `.upsert(...)` — same seeded values, same assertions, no change to what F010's test proves about AS-013/AS-031. This was a necessary, minimal, in-scope fix (my own migration under this feature's "Touches: profiles table" directly caused it) rather than scope creep into F010's test.
- **Added `zod` as an explicit `package.json` dependency** rather than relying on it being present transitively (it already was, at exactly the `^4.4.3` tech-decisions.md pins) — the first feature to actually `import` it should be the one that declares it.
- **Generated `input`/`label` via the shadcn CLI** (`npx shadcn@latest add input label`) rather than hand-authoring, consistent with how `button.tsx` was already generated and with tech-decisions.md's "shadcn/ui primitives" convention.
- **API contract split**: `signUpAction`/`signInAction` `redirect()` on success (page-flow navigation) and return `{ok:false, error_sr}` on failure (rendered inline via `useActionState`, no navigation); `resendAction` always returns `{ok, error_sr?}` JSON (never navigates) — matches the clarified "Redirects for page flows; JSON {ok,error_sr} for actions" contract.
