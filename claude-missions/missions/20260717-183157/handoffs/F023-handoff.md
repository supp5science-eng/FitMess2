## Decisions made
- **Search implemented as a single Postgres RPC function** `public.search_foods(search_query text, result_limit int default 20)`, `SECURITY INVOKER` (the default) so the caller's own session/RLS (`foods_select_all_authenticated`) governs visibility — the function never bypasses RLS. Called via `supabase.rpc('search_foods', ...)` from the SESSION-scoped client (never `createAdminClient`), matching the clarified "own-user scope enforced by RLS + session" access-control answer even though `foods` is shared-read data (every authenticated user legitimately sees every row — there is no per-user leakage risk here by design, see the migration's schema comment).
- **Ranking**: `verified desc` first (verified rows always before unverified, regardless of match quality), then `greatest(similarity, word_similarity, prefix-match-boost, brand-similarity) desc`, then `name_sr asc` as a stable final tie-break. Matches the clarified "ranked (verified rows first, then similarity desc)" scope.
- **Typo tolerance tuning (AS-038) — the one non-obvious part of this feature.** Plain `pg_trgm` whole-string `similarity()` with the default 0.3 threshold works fine for short, single-word food names ("Plazma" vs "Plazm") but FAILED to surface `"Sarma, posna, od vinovog lišća"` for the query `"sara"` — trigram similarity is normalized by TOTAL unique trigrams across both strings, so a 4-character query against a 30-character multi-word name scores far below any reasonable threshold even though the food genuinely matches. Fixed by ALSO checking `word_similarity(query, name)` (pg_trgm's best-matching-substring/word score) with a literal cutoff of `>= 0.45` — this matched `"sara"` against `"Sarma, posna, od vinovog lišća"` at `0.6`, well past the bar, while still excluding true non-matches. Verified this exact scenario live against the real seed data (see Commands run) before writing any application code.
- **Chose a literal `word_similarity(...) >= 0.45` comparison over the `<%` operator + `pg_trgm.word_similarity_threshold` GUC**, and `select set_limit(0.2)` (a RUNTIME pg_trgm function call, executed as the function body's first statement) over a function-level `set pg_trgm.similarity_threshold = 0.2` attribute. Reason (discovered empirically while tuning, cost real back-and-forth): `pg_trgm.similarity_threshold`/`pg_trgm.word_similarity_threshold` are placeholder GUCs until pg_trgm's shared library is loaded in the current backend session; attaching them as a FUNCTION-level `set` option at `CREATE FUNCTION` time only works if something earlier in the SAME session/transaction already loaded pg_trgm (this happened to be true inside the migration's own transaction, right after the `CREATE INDEX ... gin_trgm_ops` statement, but NOT true for a brand-new session — e.g. every fresh pooled connection a live RPC call gets). On a fresh session, Supabase's managed `postgres` role (not a true superuser in this environment) got `ERROR 42501: permission denied to set parameter "pg_trgm.similarity_threshold"` defining that still-unloaded placeholder. Calling `set_limit(0.2)` — a normal pg_trgm-provided function, invoked at RUNTIME inside the function body, not a DDL-time GUC declaration — sidesteps the restriction entirely and works unconditionally for any role in any session (confirmed by re-testing from several completely fresh Management-API sessions). The final `0005_food_search.sql` has a long inline comment on this exact point so a future migration author doesn't rediscover it the hard way.
- **`immutable_unaccent(text)`** — a thin `IMMUTABLE` wrapper around `extensions.unaccent()`, needed because Postgres refuses non-`IMMUTABLE` expressions in a functional index; `unaccent()` itself is only `STABLE`. Pinning `search_path = extensions, public` inside the wrapper is what makes it safe to mark `IMMUTABLE` (the resolved dictionary can never vary across calls within this function). Backs both the new `foods_name_sr_trgm_idx` functional GIN trigram index and every accent-stripping comparison inside `search_foods`.
- **Transliteration is a pure, order-independent character lookup**, not digraph-sequence detection — Serbian Cyrillic's "digraph" letters (љ, њ, џ) are each a SINGLE Unicode code point, distinct from the Latin digraphs (lj, nj, dž) they map to, so `cyrillicToLatin` never needs to look ahead/behind; it is a straightforward `for (const ch of input) out += MAP[ch] ?? ch`. This is also why it's safe to call unconditionally on every query regardless of script (AS-036's Latin queries are simply a no-op pass-through, since the lookup table only has Cyrillic keys).
- **`GET /api/foods/search?q=...`** (not POST) — a search is a read/idempotent operation, matches the RESTful convention already used by `GET /api/export`. Query validated via `zod` (`searchQuerySchema`: trimmed, 1-100 chars) — malformed/empty input gets 400 + a Serbian message, per the clarified "zod-validated inputs; reject malformed with 400 + Serbian message" answer. No-match queries return 200 + an empty list (never 404/error), per the clarified "Sensible empty response... with 200" answer.
- **Route built directly from `request.cookies`** (not `next/headers`'s `cookies()`), mirroring `GET /api/export` and `POST /api/account/delete` exactly, so it's directly callable in Vitest with a hand-built `NextRequest` — no running Next server needed for the live integration test.
- **`Database["public"]["Functions"]` in `src/lib/types/db.ts`** now types `search_foods` (previously `{ [_ in never]: never }`) so `supabase.rpc("search_foods", {...})` is fully typed end to end, matching this file's existing "additive, hand-authored, mirrors `supabase gen types`" practice from F010/F020.
- **No new UI was built.** The clarified `Touches` scope for F023 is "New route/action + lib helpers + reads existing schema" — the "dodaj hranu → pretraga" screen that will actually call this endpoint is F024+ (common-unit portion UI) and out of this feature's scope. The definition-of-done's "Manual verification: Exercise via the UI flow it powers" was therefore satisfied by directly exercising the compiled route handler (real `NextRequest`/`NextResponse`, real live-project auth + DB, no mocks) via the integration test suite rather than a browser — there is no UI flow yet for this endpoint to be manually clicked through. See Out-of-scope work needed.
- **Side-effect verification**: `search_foods` is a read-only `SELECT`-only function (no `INSERT`/`UPDATE`/`DELETE` anywhere in it or in the route) — there is no mutation to verify for "only intended rows mutated." Cross-user leakage is a non-issue by design: `foods` is `SECURITY INVOKER`-executed shared-catalog data (`foods_select_all_authenticated: using (true)`), so every authenticated user is INTENDED to see every row; the only access-control boundary this route enforces is "is there a signed-in user at all" (proven by the 401 test), which the search-and-DB layer then correctly leaves alone.
