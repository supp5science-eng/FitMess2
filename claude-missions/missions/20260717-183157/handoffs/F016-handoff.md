## Decisions made
- **Set `test.fileParallelism: false` in `vitest.config.ts`.** Adding this feature's live integration test file made three test files (F010, F015, this one) independently create Supabase Auth users and sign in against the same real project. Vitest's default concurrent file execution ran their `beforeAll` hooks at overlapping times, and their combined burst of Auth API calls intermittently tripped Supabase's shared short-window rate limit (`over_request_rate_limit`, 429) -- observed directly: `npm run test` failed with 2-3 unrelated files (including F010's pre-existing, untouched `profiles-rls.integration.test.ts`) failing on `signInWithPassword` calls returning 429, while every one of those same files passed cleanly when run individually or after waiting out the rate-limit window. This is infrastructure flakiness against a shared live external service, not a logic defect in any feature's code -- confirmed by (1) polling a throwaway sign-in attempt until Supabase's rate-limit response cleared, after which the previously-failing files passed in isolation, and (2) two consecutive full `npm run test` runs both green (27/27) after serializing file execution. Chose `fileParallelism: false` over per-test retry/backoff logic because the collision is *between* files, not within one -- no single file's retry logic can fix another file's concurrent burst; serializing execution is the one change that fixes the shared root cause for every current and future live-Supabase integration test file, at the cost of a slower `npm run test` (~85s vs ~15-25s). Did not touch F010's or F015's test files themselves -- only the shared runner config.
- **`persistOnboarding` is a plain function taking a `SupabaseClient<Database>` + `userId` + `OnboardingData`, factored out of the `"use server"` `saveOnboardingAction`.** This mirrors F011's `signInEmailPassword`/`src/lib/auth/core.ts` shape and is what let the live AS-020/AS-031 integration test call it directly against a real signed-in cookie-jar client (built the exact way F013/F015's own integration tests do), without needing a running Next server / `next/headers` request context that a plain Vitest process doesn't have.
- **Every field is re-validated and the budget is fully recomputed server-side inside `persistOnboarding`, ignoring whatever the client last rendered.** This is the "Money-math rule" (tech-decisions.md): the client's live recompute (`computeBudgetSummary`, called from `useMemo` on every edit) is purely a UI preview: the value that actually gets written to `targets` is always freshly derived from the six validated raw inputs via the same F014 engine functions, never trusted as a pre-computed number sent over the wire. Confirmed live: the integration test and the Puppeteer walkthrough both persist an *edited* set of inputs and verify the DB row's `daily_kcal` matches what the engine computes for those edited inputs, not a stale client value.
- **`saveOnboardingAction` is called directly as a plain async function from the client `SummaryScreen` (via `useTransition`), not through a `<form action>`.** There is no single natural `FormData` shape for a screen where every field is independently editable client state that also drives a live recompute (unlike F011's login/signup forms, which post once). Next.js Server Actions support being invoked as a plain function from client code exactly like this; `redirect()` inside it still works as a client-side navigation on success.
- **Chose "Započni" (not "Sačuvaj") as the primary confirm button label** — the clarified spec offered either; "Započni" ("get started") reads more naturally as onboarding's actual finish line into the app, matching the wizard's own "Završi" pattern from F015.
- **State on the summary screen is ordinary nullable `OnboardingData` (the exact same shape F015's wizard uses), not a "complete-only" type**, even though the page only ever mounts `SummaryScreen` with complete initial data. Clearing a field mid-edit (e.g. deleting the age input) degrades to the same per-field Serbian validation error the wizard shows, hiding the (now-invalid) budget preview via `isOnboardingDataComplete` + the six validators, rather than crashing `computeBudgetSummary` on a `null`.
- **AS-030's Serbian explanation text lives entirely in `explainGoalAdjustment` (UI layer), never in `engine.ts`** — this matches the F014 engine's own doc comment ("The Serbian explanation copy lives in the UI layer (F016), not here") and keeps the reason-code → sentence mapping unit-testable independent of any component.
- **`ageYearsToBirthYear` is a plain `Date`-based subtraction, not routed through a `src/lib/dates.ts` Europe/Belgrade utility** — tech-decisions.md's "never raw `new Date()` day math" rule is specifically about day/week *boundary* calculations (streaks, weekly resets); converting an already-collected age into an approximate birth year is a one-off arithmetic conversion, not a boundary computation, and no `src/lib/dates.ts` exists yet in this repo (it's listed in the planned file layout but not built by any feature so far).
