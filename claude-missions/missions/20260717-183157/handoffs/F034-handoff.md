## Decisions made
- **Soft-delete (`is_removed`/`removed_at`), not a hard DELETE**, per the feature spec's explicit "PREFER a soft-delete" scope note — existing `logs` rows already snapshot every value they display (0004_foods_logs.sql's own convention), so a hard delete would have been equally safe for log history (via `logs.food_id`'s `ON DELETE SET NULL`), but soft-delete keeps the row itself around for a future admin undo/audit feature.
- **`public.search_foods()` is re-published (not edited in place) in a new migration** (`0006_foods_removal.sql`), matching this repo's own established convention (0005 already followed this pattern relative to 0004) — Supabase migrations are append-only history; a previously-applied migration file is never edited after the fact.
- **The barcode-lookup exclusion is a plain `.eq("is_removed", false)` on `lookupFoodByBarcode`'s query** (application code), not a second SQL function — that lookup was already a simple `select().eq("barcode", ...)`, so no RPC wrapper was needed the way search's ranking logic needed one.
- **Submitter attribution shows the submitter's real email** (via `admin.auth.admin.getUserById`, since `profiles` has no email column), not just the raw UUID, degrading to "nepoznat korisnik" when `submitted_by` is null (anonymized account) or the Auth lookup itself fails — never blocks the queue from rendering.
- **Both mutation Route Handlers build a request-cookie-scoped Supabase client + call `resolveAdminSessionForClient`/`toAdminApiResult` directly**, rather than F033's `requireAdminApi()` convenience wrapper (which reads `next/headers`' `cookies()` and therefore only works inside a real Next.js request context) — this is the EXACT SAME composable admin-decision core `requireAdminApi()` uses internally (F033 exported it separately for exactly this reason), and matches every other Route Handler in this repo (`/api/foods/search`, `/api/foods/barcode/[gtin]`, `/api/logs/[id]`), which all build their session client from `request.cookies` specifically so they're directly callable from Vitest with a hand-built `NextRequest` — no running Next server needed for the route-level live tests.
- **The admin queue page (`/admin/hrana/page.tsx`) does not call `requireAdmin()` itself** — it relies entirely on `src/app/admin/layout.tsx`'s existing `requireAdmin()` call (every route nested under `/admin` inherits it), per F033's own handoff note ("or just nest it under src/app/admin/layout.tsx, which already runs it"). AS-060's "a non-admin is denied" is proven at the shared-gate level (live, in `admin-review.integration.test.ts`) and reinforced by both mutation routes' own live 403 tests.
- **`AdminFoodQueue` uses `createAdminClient()`-sourced data as server-fetched initial props**, with only the verify/remove interactions as client state (clarified data-shape answer) — a successful action removes that row from local state; no navigation, no other global state touched (proven by `test_removing_one_row_does_not_affect_a_sibling_row_no_unintended_global_state_mutation`).
