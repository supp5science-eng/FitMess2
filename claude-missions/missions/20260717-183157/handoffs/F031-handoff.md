## Decisions made
- **Reused `PortionPicker` and `POST /api/logs` completely unmodified in data flow**, per the clarified scope's explicit instruction ("Reuse F025's portion picker + POST /api/logs"). The ONLY change to `PortionPicker` was a new optional `method?: LogMethod` prop (default `"search"`, matching its existing hardcoded behavior exactly) so a caller other than the search flow can tag its own `logs.method` — `POST /api/logs` already accepted an arbitrary `method` in its request body from F025's own design, so no server-side change was needed there at all.
- **A MISS is `{ ok: true, data: null }` with a 200, never a 404**, per the clarified "sensible empty response (null) with 200" convention (same pattern `GET /api/foods/search` already established for "no results"). `ScanScreen` treats a genuine HTTP/network failure (401, 500, thrown exception) as a DIFFERENT state (a real Serbian error with retry) from a clean miss (routes to `/dodaj/novi-proizvod?barkod=<gtin>`) — a miss is never mistaken for an error, and an error never silently falls through to "unknown product."
- **Built a minimal placeholder page at `/dodaj/novi-proizvod`** (F032's own approximate file path from `plan.md`) rather than leaving the MISS route as a bare, unbuilt 404, per the clarified scope's explicit instruction ("a placeholder is fine but pass the GTIN along"). It reads and displays the `barkod` query-string param so F032 can adopt the exact same contract with zero URL-shape changes — see "Notes for the next worker."
- **Found and fixed a real, pre-existing bug in F030's `src/components/scan/barcode-scanner.tsx`** while building this feature's real (non-mocked) end-to-end evidence: `video.srcObject = stream` was being assigned to `videoRef.current` INSIDE the `start()` effect, at a point where `status` was still `"requesting"` — but the `<video>` element (and therefore `videoRef`) only exists in the JSX branch rendered once `status === "scanning"`. This meant `videoRef.current` was unconditionally `null` at that line, the `if (video)` guard silently no-op'd, and the camera stream was NEVER actually attached to any video element — `getUserMedia` would succeed, the live-looking viewfinder UI would render, but `decodeBarcode(video)` was polling an element that had received ZERO real frames (confirmed directly: `video.videoWidth`/`video.readyState` stuck at `0` indefinitely in a real headless-browser walkthrough with a real camera stream granted). In other words: **the real camera scanner could never have actually decoded a barcode in production**, despite F030's own unit/component tests passing (they mock `decodeBarcode` entirely, so this never surfaced) and F030's own manual-verification screenshot only checking that the viewfinder UI rendered (not that real frames were flowing). Fixed with a second, minimal `useEffect` keyed on `status === "scanning"` that attaches `streamRef.current` to `videoRef.current` only once that element is actually mounted (see the code comment left in place explaining exactly why the old code silently failed). Re-verified with the same headless-Edge fake-video-capture technique: post-fix, a real barcode is now genuinely decoded from a real (synthetic-but-real) camera stream. This fix does not change `BarcodeScanner`'s public contract (`onDetected`) or touch any of F030's other logic (permission-denied/error states, retry, format narrowing); all of F030's own tests for those states were re-run and still pass unmodified.
- **The 375px screenshot evidence is a genuine, real camera-decode walkthrough, not a shortcut/mock**, per the same standard F030 itself used for AS-052 (a real checksum-valid EAN-13 image, decoded by the real ZXing-WASM engine) — extended here one step further into a real live-camera *stream* (via `ffmpeg`-generated Y4M + Chromium's `--use-file-for-fake-video-capture`) so the screenshot proves the ACTUAL production code path (camera → decode → lookup → portion picker), not a component rendered directly with hand-set state.
