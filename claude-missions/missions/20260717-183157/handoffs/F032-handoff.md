## Decisions made
- **Reused `PortionPicker` and `POST /api/logs` completely unmodified**, exactly the same pattern F031 established for the scan-hit path: after a successful `POST /api/foods`, `NewProductForm` swaps itself for `<PortionPicker food={createdFood} method={createdFood.barcode ? "barcode" : "search"} />` so the user can log the just-created product immediately, per the clarified scope ("flow into the F025 portion picker"). No new `LogMethod` was needed or added — 'barcode'/'search' already exist and accurately describe how the food was FOUND for this particular log entry (via a scanned barcode vs. a bare manual add).
- **Barcode field is editable, not read-only**, per the clarified answer's explicit "(read-only or editable barcode field)" either/or — chose editable so (a) a mis-scanned/mis-typed digit can be corrected before saving, and (b) a direct/bookmarked visit to `/dodaj/novi-proizvod` with no `barkod` query param at all can still attach a barcode manually. The barcode field itself is OPTIONAL end to end (schema, form, DB column) — a user can save a product with no barcode.
- **Shared `newFoodEntrySchema` (zod) between client and server**: `NewProductForm`'s pre-submit validation and `POST /api/foods`'s server-side validation both import the exact same schema from `src/lib/food/create.ts`, so there is no possibility of the client accepting something the server then silently rejects differently (or vice versa) — matches the clarified "client-side + server-side validation; inline Serbian field errors" answer with a single source of truth for what "valid" means.
- **"Numeric/sane" bounds**: kcal_100g clamped to [0, 900] (pure fat/oil tops out ~900 kcal/100g in reality), protein/carbs/fat_100g each clamped to [0, 100] (no macro can physically exceed 100g per 100g of product). Per the clarified spec, internal kcal-consistency (protein×4 + carbs×4 + fat×9 ≈ kcal) is explicitly NOT enforced — user entries may be imperfect; an admin verifies later (`source: 'user'`, `verified: false`). Covered by `test_kcal_consistency_with_macros_is_not_enforced_user_entries_may_be_imperfect` in `create.test.ts`.
- **AS-057 uses the DATABASE's own UNIQUE constraint as the source of truth, not an application-level pre-check-then-insert**: a pre-check (SELECT then INSERT) would itself be a race condition under concurrent submissions of the same barcode. `createFoodEntry` inserts directly and classifies the resulting Postgres `23505` error (`isUniqueBarcodeViolation`), then does a SEPARATE follow-up SELECT (still via the session-scoped/RLS client) only to look up the existing food's id for the "open existing product" convenience link — that follow-up lookup is not itself a race-sensitive step (a wrong/stale id there is a minor UX inconvenience, not a data-integrity risk, since the redirect target is only ever a `select`).
- **No server-side auth check inside `/dodaj/novi-proizvod/page.tsx` itself** (unlike `/dodaj/pretraga` or `/dodaj/porcija/[foodId]`, which read user-owned server data at render time): this route has no server data of its own to fetch — `NewProductForm` is entirely client-driven and `POST /api/foods` re-verifies the session itself (401 on a missing/expired session). This matches `/dodaj/skener`'s (F030) existing precedent for a client-driven route with no auth-dependent initial render, and keeps the page trivially unit-testable (no `next/headers`/cookies() mocking needed) exactly like F031's own placeholder was.
- **Evidence-gathering used a temporary `puppeteer-core` install** (`npm install --no-save --no-package-lock puppeteer-core`, pointed at the machine's local Edge install, no Chromium download needed) rather than a permanent devDependency, matching the precedent implied by prior features' evidence directories (F024/F025 also used a "puppeteer-walkthrough.log" without adding it to `package.json`). Uninstalled immediately after (`npm uninstall puppeteer-core --no-save`) and re-ran the full test suite + `git status` to confirm zero residue in `package.json`/`package-lock.json`.
- **The evidence script marks its throwaway test user as onboarded** (`profiles.onboarded_at`) before attempting any `/dodaj/*` navigation — discovered during evidence-gathering that F013's middleware redirects any verified-but-not-onboarded session to `/onboarding` for every protected route, which would otherwise have silently redirected away from `/dodaj/novi-proizvod` without erroring (a real, easy-to-miss gotcha for any future evidence script touching `/dodaj/*` or `/danas`/`/nedelja`/`/profil`).
- **Puppeteer navigation used `waitUntil: "domcontentloaded"`, not `"networkidle0"`**: `networkidle0` never resolved against the real running server (30s timeout every time) despite the server itself responding in well under 200ms to a bare `curl` — some open connection (plausibly a PWA/service-worker-adjacent request, not investigated further since it was out of scope for this feature) kept the network "busy" from Puppeteer's point of view. `domcontentloaded` + an explicit `page.waitForSelector(...)` afterward is both faster and more reliable for this app's real pages; noted here in case a future evidence script hits the same thing.
- **AS-128 scope for this feature is "this screen only," not the full audit**: the contract's AS-128 text ("Form inputs have labels, images have alt text, and interactive elements are keyboard-reachable on core screens") is formally assigned as a range (AS-124–AS-128) to F076 (M8, dedicated accessibility audit across ALL screens), but F032's own clarified spec's Round B follow-up decisions explicitly call it out for THIS screen ("Keyboard-reachable, labeled inputs, alt text (AS-128)"). Interpreted this as: F032 must not REGRESS AS-128 on the screen it introduces, proven with real component tests (`getByLabelText` resolving to the actual input, `aria-invalid`/`aria-describedby`/`role="alert"` wiring, native-element keyboard reachability, zero unlabeled `<img>`s) — not a claim that F032 completes the full cross-app AS-128 audit, which remains F076's job.
